# AlgoSketch improvement plan

Reviewed: 2026-11-23. Baseline: `2b4d5e4` (`v1.2.1`).

## Goal and scope

Make AlgoSketch a reliable place to experiment with algorithms, understand each operation, compare approaches, and follow a structured learning path. Preserve its sketchbook identity while making the learning workspace easier to use on mobile and with a keyboard.

This change documents the assessment and proposed work, and adds contributor guidance in `AGENTS.md`. The features and fixes below remain planned unless explicitly marked complete. Priorities: **P0** correctness/release foundations; **P1** improve the existing learning experience; **P2** expand the product; **P3** optional later investment. Sizes are relative effort, not delivery promises: S = focused change, M = several related changes, L = substantial feature.

## Current assessment

The application already has a useful foundation: six sorting visualizers, two searching visualizers, stack/queue/linked-list operations, detailed MDX lessons, code examples in five languages, statistics, multiple visualization modes, theme-aware styling, and a production service worker. Algorithm implementations are separated from the rendering components, making focused correctness tests practical.

The main opportunity is to turn these individual lessons into a consistent experimentation and learning experience. The homepage explains the product but does not demonstrate a live algorithm. The dashboard emphasizes sorting/searching and omits a comparable data-structure section. Algorithm pages place lengthy explanations before the interactive visualizer. Controls and playback logic are repeated across algorithms, and educational statistics need stronger correctness guarantees.

### Browser findings

Production Chromium checks at 1440 × 1000 returned HTTP 200 for all 18 existing pages and HTTP 404 for an unknown route, with no uncaught page errors observed. Bubble sort supported next/previous, switching to nodes, start/pause, and regeneration. The rewind defect reproduced directly: comparisons changed from 0 to 1 after Next, then stayed at 1 after Previous returned to step 0. Stack push, queue enqueue, linked-list insertion, and their reset controls were exercised.

Six representative pages were also checked at 390 × 844. The Nodes view button extends beyond the viewport on bubble and heap lessons even though document-level overflow checks pass. This needs a visible-content check, since horizontal overflow hiding can conceal the issue. The inspected dashboard and linked-list mobile layouts had no clipped buttons/headings/inputs in this small sweep. The dashboard uses nested `<main>` landmarks, and structure pages start at `<h2>` without an `<h1>`.

The production service worker registered and controlled the page; a previously visited bubble-sort lesson reloaded offline successfully. The browser actually links `/manifest.webmanifest`, which returns HTTP 200: Next.js file-based metadata overrides the stale `/manifest.json` setting in the source. `/manifest.json` itself returns 404. This is source cleanup and a future regression risk, **not a confirmed broken manifest in the running build**. Full installability, uncached offline fallback, service-worker updates, cross-browser behavior, and automated contrast/performance audits remain unverified.

## Delivery sequence

### Milestone 1 — correctness and a repeatable release baseline

Complete this before major feature expansion.

- [ ] **R6: Add project checks (M).** Introduce an explicit typecheck script, configured ESLint, a TypeScript unit-test runner, and Playwright. Preserve the Bun lockfile and document the supported runtime/package-manager versions. CI runs a frozen install, lint, typecheck, tests, production build, and a focused browser suite. Review framework/dependency support and relevant advisories while establishing the baseline; validate MDX, React, Tailwind, and Serwist compatibility when upgrading.
- [ ] **R1–R4: Repair educational correctness (M).** Fix empty/singleton behavior, pointer connections, snapshot mutation, and reversible statistics. Give comparison, swap, write, shift, and traversal events distinct meanings. Include independent expected results for small known examples rather than asserting only against the same step flags used by the UI.
- [ ] **PWA release checks (S).** Preserve the verified manifest route and cached offline reload; fix offline precache revisioning and test uncached fallback. Check whether plugin-provided registration and the custom registration component duplicate update handling. Track the stale source declaration as R5 cleanup in milestone 2.
- [ ] **Lock in regressions (M).** Test empty/singleton/sorted/reversed/duplicates/boundaries, input immutability, final values, intermediate invariants, valid pointers, and exact operation counts. Verify next→previous→next restores the identical snapshot and counts.

Exit criteria: all configured checks pass unattended; no known P0 correctness defects remain; every algorithm can complete, pause, rewind, regenerate, and survive route changes without stale timers. Verify a production cached-page reload offline and a first-visit fallback separately from installability.

### Milestone 2 — a better workspace for the existing catalog

- [ ] **Unified playback and timeline (P1, L; depends on R1–R4).** Extract a typed playback hook and shared controls incrementally, starting with bubble sort and linear search. Add restart with the same input, first/last step, timeline scrubbing, visible speed values, and keyboard shortcuts. Derive metrics from snapshots and prevent multiple timers. Then migrate the remaining visualizers while retaining their specialized tree/partition views.
- [ ] **Custom inputs and reproducible presets (P1, M; depends on generator edge cases).** Accept validated comma/space-separated arrays and provide sorted, reversed, nearly sorted, repeated-value, and seeded-random presets. Explain supported limits and binary search's sorted-input requirement. Show inline errors and preserve valid work after an invalid submission. Test integer parsing without silent decimal truncation.
- [ ] **Visualizer-first lesson layout (P1, M).** Put the interactive example near the top with an accessible Learn/Visualize/Code navigation or split layout on wide screens. Keep the current jump-to-visualizer action, add a small contents list, and make controls easy to reach on mobile. Preserve readable prose width and the sketchbook visual identity.
- [ ] **Accessibility and responsive pass (P1, M; includes R8/R12).** Add properly labeled keyboard sliders, accessible sidebar expand/collapse buttons and logo navigation, logical page headings, visible focus, restrained status announcements, patterns/text alongside colors, and reduced-motion support. Audit text contrast after entry animations settle. Contain wide diagrams/code within labeled scroll areas rather than hiding meaningful content.
- [ ] **Theme preference (P1, S).** Add an obvious light/dark/system control, persist the choice, and verify code highlighting, diagram labels, contrast, and hydration in each mode.
- [ ] **Catalog and discovery (P1, M).** Create one typed algorithm/data-structure registry for names, routes, difficulty, prerequisites, complexity, supported views, and availability. Drive navigation, catalog cards, dashboard counts, and relevant metadata from it. Add a data-structures dashboard section, clickable algorithm entries, search, and difficulty/category filters with a useful empty state.
- [ ] **Rendering and loading improvements (P1, M; includes R7/R9).** Remove the blanket hydration gate, preserve item IDs, and measure a production baseline before optimization. Lazy-load expensive code highlighting or specialized views where useful; distinguish algorithm memory complexity from the simulator's stored history. Recheck on a throttled mobile profile. The current algorithm routes report approximately 395–397 kB first-load JS in the build output.
- [ ] **Documentation and metadata cleanup (P1, S; includes R5/R10/R11).** Reconcile outdated contributor examples and middleware docs; check canonical URLs, sitemap, Open Graph previews, footer repository target, and homepage feature claims against implemented behavior.

Exit criteria: a learner can find any current topic, load a chosen dataset, control the run with pointer or keyboard, inspect accurate counts, switch theme/view, and read the explanation comfortably at 390 px and desktop widths. Add 320 px and tablet regression checks before calling the layout fully responsive.

### Milestone 4 — expand the catalog in coherent releases

Add one family at a time. Every new topic needs a correct step generator, visual explanation, input controls, legend, complexity/prerequisite notes, appropriate code samples, navigation, and regression coverage before being listed as available.

1. **Trees and heaps (P2, L):** binary search tree insert/search/delete, DFS traversals, level-order traversal, and heap/priority-queue operations. Reuse existing heap rendering where suitable. Check duplicate policy and empty-root/single-child/two-child deletion cases.
2. **Graphs and pathfinding (P2, L):** editable small graphs, BFS/DFS, then Dijkstra for nonnegative weights. Show visited/frontier/current-path states and disconnected-node outcomes. Bound graph size; test cycles and unreachable destinations. Add A\* only after explaining its heuristic assumptions.
3. **Hash tables and more linear structures (P2, M–L):** collision handling, circular queue/deque, and doubly linked lists. Explain load factor and resizing rather than implying every operation is unconditionally constant time.
4. **Recursion and dynamic programming (P2, L):** call-stack traces, memoized versus naive Fibonacci, then small grid/knapsack examples with visible recurrence and dependencies. Bound exponential examples and provide cancel/reset.
5. **Additional sorting/searching (P3, M):** counting/radix sort, lower/upper bound, and quickselect when they support a clear learning goal. Explain domain restrictions, duplicate semantics, and algorithm-specific tradeoffs.

## Later ideas and product boundaries

- **P3:** teacher presentation mode, exercise import/export, internationalized lesson content, and image/short-animation export. Decide on accessible export descriptions and verify the rendered artifact before offering downloads.
- **P3:** optional account synchronization only after local progress proves useful. Define privacy, deletion, conflict handling, and the backend model before introducing authentication.
- **P3:** an executable code playground only after selecting a constrained execution environment with time/memory limits. Editable examples and verified copyable snippets can ship earlier without running arbitrary code.
- Keep the core visualizers usable without accounts, paid services, or AI-generated explanations. New integrations should solve an observed learner need.

## Validation and definition of done

- **Algorithms:** independent expected outputs and metrics; immutable inputs/snapshots; identity and pointer invariants; supported boundary inputs; deterministic seeded fixtures. Add property-based/randomized cases after the small regressions are reliable.
- **Playback:** first/last, next/previous, scrub, pause/resume, speed changes, same-input restart, regenerate, view/language switching, completion, and unmount cleanup. Assert that state and counts depend only on the selected snapshot.
- **Browser:** homepage→catalog→lesson, search/filter empty states, actual input operations, copying examples, theme persistence, browser back/forward, and unknown-route recovery. Cover supported mobile/tablet/desktop sizes; include keyboard and reduced-motion checks. Add Firefox/WebKit to release coverage when tooling is configured.
- **PWA:** run against `build` + `start`; validate the linked manifest/icons; verify service-worker installation, cached and uncached offline navigation, reconnection, and update behavior without silently discarding a running experiment.
- **Performance/accessibility:** record Lighthouse/axe results once tooling exists, then set budgets from measured production baselines. Manually inspect focus order, announcements, contrast, clipping, and touch targets; automated checks alone do not establish WCAG compliance.
- **Delivery:** lint, types, relevant tests, and production build pass; document remaining limitations; update catalog/docs and mark completed roadmap items with evidence. Any commits use the exact author/committer identity in `AGENTS.md`.

## Recommended first implementation slice

Set up noninteractive lint/typecheck/unit/browser commands and CI, then fix R1–R4 and the offline precache warning with small regression tests. Follow with accessible shared controls and custom datasets for bubble sort and linear search. Those two examples establish the reusable behavior for the remaining catalog and the later comparison feature.
